# L3-A — JS 通用解析层

## 总体判断

- **评审范围**：`cli.mjs` 的分发、`cc run/introspect/rebuild`，以及 `lib/bun-binary.mjs`、`module-graph.mjs`、`extract.mjs`、`split.mjs`、`layout.mjs`、`diff.mjs`、`beautify.mjs`、`naming.mjs`、`hook.mjs`、`lib/probes/*.cjs`；仅为判断 `bun-binary` 的反向依赖读取了 `lib/patch/io/raw-reader.mjs`，未评审其余 `lib/patch/**`。
- **已读取/执行的证据**：逐文件读取上述实现及对应 `test/*.mjs`、`docs/FINDINGS-phase0.md`、`docs/ARCHITECTURE.md`；运行 17 个范围内测试文件，共 **65 pass / 0 fail / 32956 assertions**；另做独立 PoC 验证 module-graph 越过 `.bun` 仍被接受、split 顶层 lookalike 与混合 arity 误分类、diff 的真实 split hash 无法识别 minifier 改名、`cc run` 吞掉扩展加载失败、probe 写盘失败仍返回成功、split 重跑遗留旧模块文件、空 anchor 的 `Buffer.indexOf` 不前进、ELF 非法 section 范围被接受。
- **总体 verdict**：**修复 Major 后可进入下一阶段**。
- **Blocker 数量**：**0**。
- **计数**：Blocker 0，Major 7，Minor 5，Note 2。
- **肯定项**：trailer 尾窗搜索与 double-magic 正样本、`graph_base = offsets_start - byte_count`、52 字节记录与 `entry_point_id` 前置校验、mmap 主路径与 pread 回落、used-after-close、extract 的 reader 复用、`runExtract`/`runSplit` 的主调用链 `await`、分批并发写盘、hook 等长与逐 site 换行守卫、`execFileSync`/`spawn` 数组参数均有实测覆盖。测试并非整体假绿，但下列缺口证明“全绿”尚不能作为正确性结论。

## 遗留给 L4 的线索

1. **真实多版本 corpus**：当前 helper 测试只跑本机活版本 2.1.217；P0 文档声称 195/201/205/206 验证，但仓库测试未冻结这些 app/AST 事实。L4 应用至少两个异版本、异 minifier handle 的真实 index 做端到端 split→diff，重点验证 L3A-03、L3A-04。
2. **破坏性 graph mutation matrix**：为 `Offsets.byte_count/mpOff/mpLen/entryPointId`、record name/content offset/length、loader byte 各做单字段 mutation，并确认每个坏输入由对应 parser guard 失败，而不是先被 ELF 截断或测试夹具失效偶然挡住。尤其验证指针不能逃出 `.bun` graph 区。
3. **CLI 失败传播 E2E**：通过真正的 `bun cli.mjs cc run/introspect` 验证缺 ext、ext throw、probe 无 marker、probe 写盘失败、child signal 等都得到非零进程退出；不要只断言返回对象。
4. **输出事务性**：对 extract/split/assets/layout 的现有 outdir 重跑、磁盘满、权限错误、单文件写失败做故障注入，确认不会留下新 manifest/index 指向半成品，也不会混入旧代文件。
5. **静态层输入信任边界**：把目标二进制视为不可信解析输入，统一审查所有由 blob name/version/handle 派生的路径；L3A-07 已证明 version 可逃逸，assets 的 `basename` 与 split 的 handle sanitize 相对更安全，但仍需端到端 root containment oracle。
